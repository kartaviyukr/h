# Фаза 3 — План: Генерация персонального меню (DeepSeek)

> Статус: **ожидает подтверждения**. Код не пишется до утверждения этого плана.

## Цель фазы
По профилю пользователя (цели КБЖУ, аллергии/исключения, бюджет, цель) сгенерировать
персональное меню на N дней через **DeepSeek** (LLM), провалидировать и
скорректировать КБЖУ под цели, сохранить меню в БД и отдать через API.

Только бэкенд. RAG по реальной базе рецептов, сравнение цен и корзина —
последующие фазы. Flutter-экраны — отдельная UI-фаза.

## Что в рамках / вне рамок
**В рамках Фазы 3:**
- Интеграция с DeepSeek (chat completions, структурированный JSON-ответ).
- Сборка промпта из профиля (цели, аллергии, бюджет, предпочтения).
- Валидация ответа строгой Pydantic-схемой меню.
- Коррекция КБЖУ под цели (см. ниже).
- Сохранение меню в БД + история, эндпоинты генерации/чтения.
- Тесты с моком DeepSeek (без реальных сетевых вызовов).

**Вне рамок (последующие фазы):**
- RAG/векторный поиск по реальным рецептам (farm.ipynb как источник) — Фаза 4.
- Сравнение цен между сервисами доставки РФ — Фаза 5.
- Корзина и дип-линки — Фаза 6.
- Flutter-экраны меню — UI-фаза.

## Слои (по архитектуре)
```
api/menu.py            роуты генерации/чтения меню
services/menu_service  оркестрация: профиль → промпт → DeepSeek → валидация → коррекция → сохранение
services/nutrition     расчёт/коррекция КБЖУ (чистая логика, без сети)
integrations/deepseek  клиент DeepSeek (единственное место сетевых вызовов к LLM)
repositories/menu_repo доступ к БД меню
models/menu            ORM-модель(и) меню
schemas/menu           Pydantic: запрос, ответ, схема LLM-вывода
```

## Интеграция с DeepSeek
- `integrations/deepseek.py`: тонкий клиент поверх HTTP (`httpx`) к
  `https://api.deepseek.com/chat/completions`, модель `deepseek-chat`.
- Ключ — `DEEPSEEK_API_KEY` из `.env` (поле уже есть в config).
- Структурированный вывод: `response_format={"type": "json_object"}` + явная
  JSON-схема в системном промпте; ответ парсим в Pydantic `LlmMenu`.
- Таймаут, базовый ретрай при 5xx/таймауте (1-2 попытки).
- Сеть: вызовы DeepSeek требуют исходящего доступа — зависит от network policy
  окружения. В тестах клиент **мокается**.

## Коррекция КБЖУ (требование ТЗ «коррекция КБЖУ»)
`services/nutrition`:
1. Суммируем КБЖУ по дню из позиций меню.
2. Сравниваем с `target_*` из профиля; если отклонение по калориям > допуска
   (предлагаю ±10%) — **масштабируем граммовки** позиций пропорционально, чтобы
   попасть в цель (простая и предсказуемая логика, без повторного вызова LLM).
3. Пересчитываем итоговые КБЖУ и кладём в ответ + флаг `adjusted: true/false`.

Альтернатива (на обсуждение): вместо масштабирования — повторный промпт DeepSeek
с указанием «попади в КБЖУ точнее» (дороже, медленнее, недетерминированно).
Рекомендую масштабирование.

## Модель данных
Предлагаю хранить меню как **валидированный JSONB** + поля верхнего уровня для
выборок (меньше кода сейчас; нормализация ингредиентов — в Фазе 5 под корзину).

### menus
| поле | тип | примечание |
|------|-----|-----------|
| id | UUID PK | gen_random_uuid() |
| user_id | UUID FK → users.id (cascade) | владелец |
| title | text | напр. «Меню на 3 дня» |
| days_count | int | число дней |
| status | text | `ready` / `failed` |
| params | JSONB | снапшот целей/ограничений на момент генерации |
| payload | JSONB | само меню (валидируется схемой `MenuOut`) |
| created_at | timestamptz | |

Альтернатива — полная нормализация (`menu_days`, `menu_meals`,
`menu_ingredients`). См. открытый вопрос 4.

## Схема меню (Pydantic, она же контракт для LLM)
```
MenuOut
  days_count: int
  total_per_day: Macros           # средние КБЖУ/день
  days: list[MenuDay]
MenuDay
  day_index: int
  totals: Macros
  meals: list[Meal]
Meal
  type: breakfast|lunch|dinner|snack
  title: str
  ingredients: list[Ingredient]   # name, amount, unit
  steps: list[str]                # краткий рецепт
  macros: Macros
  est_cost_rub: Decimal | None    # грубая оценка LLM (уточним в Фазе 5)
Macros: kcal, protein_g, fat_g, carbs_g
Ingredient: name, amount, unit
```
Учёт ограничений: аллергии/исключения и бюджет передаются в промпт; в валидации
проверяем, что в ингредиентах нет явных аллергенов из профиля (мягкая проверка).

## Эндпоинты (все под Bearer-токеном, только свои меню)
- `POST /menu/generate` — body `{days_count?: int=3, meals_per_day?: int=3, note?: str}`
  → генерирует, сохраняет, возвращает `MenuOut` + `id`.
- `GET /menu` — список меню пользователя (кратко: id, title, days_count, created_at).
- `GET /menu/{id}` — полное меню (payload). 404 если чужое/нет.

## Миграция
- Alembic `0002_menus`: таблица `menus` (+ индекс по `user_id`, `created_at`).

## Конфиг / .env
- Используем существующий `DEEPSEEK_API_KEY`.
- Добавим в config: `deepseek_base_url` (default `https://api.deepseek.com`),
  `deepseek_model` (default `deepseek-chat`), `deepseek_timeout_s`.
- В `.env.example` — заполним пустыми/дефолтами.

## Тесты
- `nutrition`: масштабирование под цель, расчёт сумм, граница допуска.
- `menu_service` с **моком** DeepSeek: успешный парс валидного JSON; ошибка
  парсинга → `status=failed`/4xx; учёт аллергий.
- API: `POST /menu/generate` (мок) → 200 + сохранено; `GET /menu`/`/menu/{id}`
  отдают своё, 404 на чужое, 401 без токена.

## CI
- Тесты гоняются с замоканным DeepSeek (без сети), на Postgres-сервисе (как в Фазе 2).
