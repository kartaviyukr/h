# Фаза 4 — План: RAG по рецептам (pgvector + локальные эмбеддинги)

> Статус: **ожидает подтверждения**. Код не пишется до утверждения этого плана.

## Решения (подтверждено)
- **Источник рецептов**: поиск/сбор из интернета → формируем собственный корпус.
- **Эмбеддинги**: локальная модель (sentence-transformers), без внешних API.

## ⚠️ Ограничения окружения (важно)
В этом контейнере фильтрующий прокси: внешние сайты и PyPI отдают **403**.
Поэтому:
- **Ингестию рецептов из интернета и локальные эмбеддинги здесь запустить нельзя**
  (нет сети к сайтам и нельзя поставить `sentence-transformers`/torch).
- Я пишу код и тесты (с моками), но **реальная сборка индекса** выполняется там,
  где есть сеть и зависимости: локально у тебя или в окружении с другой network
  policy. В README дам команды.
- Чтобы CI оставался быстрым и без сети: тяжёлый `sentence-transformers` — в
  **опциональном** extra `[rag]`, импортируется лениво; тесты используют **fake-эмбеддер**.

## Цель фазы
Построить корпус рецептов (ингестия из интернета), индексировать его векторно в
pgvector локальными эмбеддингами и использовать **retrieval** для «приземления»
генерации меню: DeepSeek получает реальные подходящие рецепты как основу, а не
выдумывает блюда с нуля.

## Слои (по архитектуре)
```
models/recipe.py            ORM-модель рецепта + векторная колонка (pgvector)
integrations/embeddings.py  интерфейс эмбеддера + локальная реализация (lazy, extra [rag])
integrations/recipe_source.py  загрузка рецептов из интернета (fetch + парсинг JSON-LD)
repositories/recipe_repo.py доступ к БД + векторный поиск (<=> cosine)
services/recipe_index.py    ингестия (fetch→normalize→embed→upsert) и retrieval(query→top-k)
services/menu_service.py    интеграция RAG: retrieve → передать рецепты в промпт DeepSeek
app/scripts/ingest_recipes.py  CLI-скрипт построения индекса (запускается вне CI)
```

## Источник рецептов («поиск в интернете»)
Сборка корпуса — **разовый/периодический** скрипт ингестии:
1. Конфигурируемый список источников (seed URL рецептов или поисковые запросы).
2. Для каждого URL — HTTP-загрузка HTML, извлечение **schema.org Recipe** из
   `<script type="application/ld+json">` (большинство кулинарных сайтов отдают
   структурированные данные — устойчивее, чем парсить вёрстку).
3. Нормализация → наша схема рецепта (название, ингредиенты, шаги, КБЖУ, теги).
4. Эмбеддинг текста рецепта локальной моделью → upsert в БД.

Открытый вопрос: брать ли список URL из конфигурации (seed-список, рекоменд. для
v1) или подключать поисковый API (выдаёт URL по запросу) — см. вопросы ниже.

## Эмбеддинги (локальные)
- Интерфейс `Embedder.encode(texts: list[str]) -> list[list[float]]`.
- Реализация по умолчанию: `sentence-transformers` модель
  `paraphrase-multilingual-MiniLM-L12-v2` (**384 dims**, мультиязычная, лёгкая).
  Импорт ленивый; пакет — в extra `[rag]`.
- Размерность вектора фиксируется в конфиге `embedding_dim` (= 384) и в миграции.
- Тесты: `FakeEmbedder` (детерминированные векторы нужной размерности), без torch.

## Модель данных

### recipes
| поле | тип | примечание |
|------|-----|-----------|
| id | UUID PK | gen_random_uuid() |
| title | text | название |
| ingredients | JSONB | [{name, amount, unit}] |
| steps | JSONB | список шагов |
| macros | JSONB | КБЖУ на порцию |
| tags | text[] | кухня/диета/категории |
| source_url | text NULL | откуда взят |
| content_hash | text UNIQUE | дедуп при повторной ингестии |
| embedding | vector(384) | pgvector |
| created_at | timestamptz | |

Индекс для поиска: `ivfflat`/`hnsw` по `embedding` (cosine). Текст для эмбеддинга —
`title + ингредиенты + теги`.

## Миграция
- `0003_recipes`: `CREATE EXTENSION IF NOT EXISTS vector` (для прод/Supabase;
  локально уже есть в `db/init`), таблица `recipes`, векторный индекс
  (`USING hnsw (embedding vector_cosine_ops)`), уникальный `content_hash`.
- Зависимость `pgvector` (python) — лёгкая, в основные зависимости (нужна для типа
  колонки и миграции). `sentence-transformers` — в extra `[rag]`.

## Retrieval и интеграция в генерацию меню
- `recipe_index.retrieve(query_text, k)`: эмбеддинг запроса → `ORDER BY embedding
  <=> :q LIMIT k`.
- В `menu_service.generate`: формируем запрос из профиля (цель, КБЖУ, исключения),
  достаём top-k рецептов, передаём их в системный/пользовательский промпт DeepSeek
  как «используй эти проверенные рецепты как основу, не предлагай исключённые
  продукты». Если индекс пуст / retrieval недоступен — **graceful fallback** на
  чистую LLM-генерацию (как в Фазе 3), меню всё равно создаётся.
- Сохраняем в `menus.params` список `recipe_ids`, использованных как контекст
  (трассируемость).

## Конфиг / .env
- `EMBEDDING_MODEL` (default `paraphrase-multilingual-MiniLM-L12-v2`).
- `EMBEDDING_DIM` (default 384).
- `RAG_TOP_K` (default 5).
- `RAG_ENABLED` (default true; можно выключить — тогда чистый LLM как в Фазе 3).
- Источники ингестии: путь к файлу seed-URL или список в env (обсуждаемо).

## CLI ингестии
`python -m app.scripts.ingest_recipes --source <seed.txt> [--limit N]`
- Запускается локально/в окружении с сетью и установленным extra `[rag]`.
- Идемпотентно: дедуп по `content_hash`, upsert.
- README: как поставить `pip install -e ".[rag]"` и запустить.

## Тесты (CI, без сети и без torch)
- `recipe_repo`/`recipe_index`: с `FakeEmbedder` засеять несколько рецептов с
  известными векторами, проверить, что retrieval возвращает ближайшие в нужном
  порядке (на Postgres-сервисе с расширением `vector`).
- `recipe_source`: парсинг schema.org JSON-LD из фикстуры HTML (offline, без сети).
- `menu_service` с RAG: мок эмбеддера + мок DeepSeek → retrieved-рецепты попадают
  в промпт; пустой индекс → fallback на чистую генерацию (200, меню есть).
- conftest: добавить `CREATE EXTENSION IF NOT EXISTS vector` и `recipes` в TRUNCATE.
