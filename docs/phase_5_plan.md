# Фаза 5 — План: Сравнение цен между сервисами доставки (РФ)

> Статус: **ожидает подтверждения**. Код не пишется до утверждения этого плана.

## Цель фазы
По ингредиентам сгенерированного меню оценить стоимость закупки в нескольких
сервисах доставки РФ и **сравнить** итог по сервисам (где дешевле собрать корзину).
Формирование самой корзины и дип-линки — Фаза 6.

## ⚠️ Реальность интеграций (важно — определяет дизайн)
У сервисов доставки РФ (Самокат, СберМаркет/Купер, Яндекс Лавка, ВкусВилл, Озон
Свежее, Перекрёсток Впрок и т.п.) **нет публичных официальных API цен**. Доступ —
это парсинг/неофициальные эндпоинты, привязка к региону, антибот-защита и ToS.
Плюс в этом окружении прокси отдаёт **403** на внешние сайты.

Поэтому Фаза 5 строится как **расширяемая абстракция провайдеров цен**, а не как
готовые боевые интеграции:
- Единый интерфейс `PriceProvider` + матчинг ингредиент→товар + нормализация единиц.
- Рабочий `StaticPriceProvider` (локальный каталог-файл) — для разработки, демо и
  тестов, без сети.
- Боевые адаптеры конкретных сервисов — отдельные PRّы позже, в окружении с сетью;
  каждый прячется за тем же интерфейсом. В тестах/CI — фейковые провайдеры.

## Слои (по архитектуре)
```
integrations/price/base.py        PriceProvider (Protocol), ProductOffer, dataclasses
integrations/price/static.py      StaticPriceProvider (каталог из файла/таблицы)
integrations/price/registry.py    реестр доступных провайдеров
services/units.py                 нормализация единиц и расчёт стоимости количества
services/pricing.py               матчинг ингредиентов, сбор корзины, сравнение по сервисам
repositories/price_repo.py        кэш офферов и сохранённых сравнений
models/pricing.py                 product_offers (кэш), basket_quotes (результат сравнения)
api/pricing.py                    POST /menu/{id}/prices, GET /menu/{id}/prices
```

## Поток данных
1. Берём меню пользователя (`menus.payload`), собираем **агрегированный список
   ингредиентов** по всем дням: `{name, amount, unit}` (из структуры Фазы 3),
   суммируем одинаковые позиции.
2. Для каждого провайдера: по каждому ингредиенту ищем лучший товар (`search`),
   нормализуем единицы и считаем стоимость нужного количества.
3. Агрегируем корзину по провайдеру: итог, число найденных/ненайденных позиций.
4. Сравниваем провайдеров (сортировка по итогу), помечаем самый дешёвый.
5. Сохраняем результат (`basket_quotes`) и отдаём в API.

## Нормализация единиц (`services/units.py`)
- Базовые группы: масса (г/кг), объём (мл/л), штуки (шт/уп).
- Оффер товара: цена за упаковку + размер упаковки в базовой единице.
- Стоимость позиции = по упаковкам (нужно купить целые упаковки):
  `ceil(required / package_size) * package_price` — это **реальная** стоимость.
  Параметр `proportional=true` (опц.) — пропорциональный расчёт для грубого сравнения.
- Несовпадение групп единиц (рецепт в «шт», товар в «кг») → позиция помечается
  «не сматчена», не ломает расчёт.

## Матчинг ингредиент → товар (v1 — простой)
- Нормализация строки (нижний регистр, убрать количество/единицы, стоп-слова),
  поиск по нормализованному названию в каталоге провайдера.
- Если несколько — берём дешёвший за базовую единицу.
- Фаззи/эмбеддинг-матчинг — позже (можно переиспользовать инфраструктуру Фазы 4,
  но локальные эмбеддинги тут не запустить — оставляем на потом).

## Эндпоинты (под Bearer, только свои меню)
- `POST /menu/{id}/prices` — посчитать и сохранить сравнение (по доступным
  провайдерам; опц. body `{providers?: [...], proportional?: bool}`).
- `GET /menu/{id}/prices` — последнее сохранённое сравнение (404, если нет).

Формат ответа: список провайдеров с `total_rub`, `matched`/`unmatched` позициями,
плюс `cheapest_provider`.

## Конфиг / .env
- `PRICE_PROVIDERS` — список включённых провайдеров (default: `static`).
- `PRICE_CATALOG_PATH` — путь к файлу-каталогу для `StaticPriceProvider`
  (напр. `data/price_catalog.json`), шаблон кладём в репо.
- `PRICE_CACHE_TTL_H` — TTL кэша офферов (для боевых провайдеров позже).

## Миграция
- `0004_pricing`: таблицы `product_offers`, `basket_quotes` (+ индексы:
  `product_offers(provider, query)`, `basket_quotes(menu_id)`).

## Тесты (CI, без сети)
- `units`: упаковочный расчёт (округление вверх), пропорциональный, несовпадение групп.
- `pricing` со `StaticPriceProvider` (фикстура-каталог): матчинг, агрегация
  одинаковых ингредиентов, выбор самого дешёвого провайдера, ненайденные позиции.
- API: `POST /menu/{id}/prices` → 200 + сохранено; `GET` → отдаёт; 404 на чужое;
  401 без токена.
- conftest: добавить `product_offers`, `basket_quotes` в TRUNCATE.
